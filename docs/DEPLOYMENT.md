# Deployment

Docker Compose is the primary evaluation route (one command, nothing to sign up for). The
hosted demo runs the same images on Render's free tier against a Neon Postgres project.

## 1. Docker Compose (primary)

```bash
cp .env.example .env            # optional: change POSTGRES_PORT if 5432 is taken
docker compose up --build       # postgres, api, mocks, web
```

What happens on first boot:

1. `postgres` starts and passes its health check.
2. `api` runs `prisma migrate deploy`, then (because `SEED_ON_BOOT=true`) the compiled seed
   with `--if-incomplete`: roles, users, demo data and twelve months of summaries. A
   database whose seed finished is left alone on later boots; an interrupted seed is
   completed, because every seeder skips the data it finds.
3. `mocks` and `web` (nginx on 8080, proxying `/api/*` to the api container) come up.

Then open http://localhost:8080 and log in with a user from the README table. Callbacks from
the mock channels reach the API inside the Compose network (`API_PUBLIC_URL=http://api:3000`).

Verification checklist (what phase 7 ran from a clean clone):

```bash
curl -s localhost:8080/api/health            # {"status":"ok",...}
curl -s localhost:8080/api/ready             # db + queue up
# log in, initiate an online payment of 12.00 via the UI → it flips to CONFIRMED within ~3 s
curl -s -H "authorization: Bearer <token>" localhost:3000/audit/verify   # {"ok":true,...}
```

Reset everything: `docker compose down -v` (drops the database and the storage volume).

## 2. Hosted demo: Render + Neon

The blueprint `render.yaml` declares three services; the live instance is
https://ircub-web.onrender.com (api https://ircub-api.onrender.com, mocks
https://ircub-mocks.onrender.com). Click-path, in order:

### 2.1 Neon (database)

1. https://neon.tech → New project → name `ircub`, region closest to Render's `frankfurt`.
2. Project dashboard → **Connect** → tick **Pooled connection** and copy the plain
   `postgresql://…` string exactly as shown. It already carries `?sslmode=require` (and on
   newer projects `&channel_binding=require`); do not append anything. Prisma uses the
   `public` schema by default.
3. Nothing else: migrations run on every api deploy, pg-boss creates its own `pgboss`
   schema on first start (verified against Postgres 16; Neon runs 16/17).

### 2.2 Render (api, mocks, web)

1. https://render.com → New → **Blueprint** → connect the GitHub repository → Render reads
   `render.yaml` and lists `ircub-api`, `ircub-mocks`, `ircub-web`.
2. Render shows one field it cannot fill from the blueprint (`sync: false`): paste the
   Neon string into `ircub-api` → `DATABASE_URL`. It goes into Render's dashboard only,
   never into `render.yaml` or any file in the repository. Secrets (`JWT_SECRET`, `JWT_REFRESH_SECRET`, `MOCK_SHARED_SECRET`) are
   generated by Render; the mocks and api share the same `MOCK_SHARED_SECRET` through
   `fromService`.
3. Apply. The first deploy builds the three images/bundles (5–8 minutes on the free tier).
   `SEED_ON_BOOT=true` seeds the Neon database on the api's first start; `--if-incomplete`
   keeps later deploys from reseeding once the seed has finished.
4. If the static site's name is not `ircub-web`, update the rewrite destination in
   `render.yaml` (`https://<api-service>.onrender.com/*`) and redeploy the web service.
5. Open the web URL and log in. Swagger: `https://<api>.onrender.com/docs`; mock outbox:
   `https://<mocks>.onrender.com/outbox`.

Free-tier behaviour to tell the panel:

- Services sleep after 15 minutes idle; the first request takes ~1 minute (cold start). Open
  the web URL, wait for "API is waking up…" to clear.
- Crons (FX refresh, nightly batches, reconciliation, summaries, alerts) run only while the
  api is awake; the UI buttons (Build for date, Run reconciliation, Evaluate alerts) do the
  same work on demand.
- The api's storage (bill PDFs, uploaded CSVs) is ephemeral on Render; PDFs are re-rendered
  lazily when missing.

### 2.3 Demo password on the hosted instance

`render.yaml` gives `ircub-api` a generated `SEED_PASSWORD`. On every boot the container
rewrites the six demo users' password to it (`seed.js --users-only`), so the hosted demo
never accepts the password printed in the README. To read or rotate it: Render → `ircub-api`
→ **Environment** → `SEED_PASSWORD` (reveal, or set a new value and redeploy). Share it with
the panel in the submission note, not in the repository.

### 2.4 Reseeding the hosted database

Render shell on `ircub-api`:

```bash
node dist/seed/prisma/seed.js        # without --if-incomplete: refreshes reference data, skips demo data that exists
```

To start from scratch, reset the Neon project (Neon dashboard → Branches → reset) and
redeploy the api; `SEED_ON_BOOT` seeds it again.

## 3. Environment variables

Every variable the api reads is validated at boot by `apps/api/src/config/env.schema.ts`
and documented in `.env.example`. `SEED_ON_BOOT` is read by the container entrypoint only.
